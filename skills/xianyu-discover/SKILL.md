# 闲鱼选品发现

先读取工作台数据，再决定下一步。用户运行本 skill 时，默认由 agent 内部完成认领方向、扩词、采样、初筛和需求判断，最终直接交付选品结果；不要把普通中间步骤转交给用户。目标是让样本形成有依据的商品机会，不能以“采样已入库”替代完成选品。

当前工作台目录见 [references/workbench.md](references/workbench.md)。第一次使用或修改数据前阅读该文件，使用 `scripts/workbench.py` 读取状态及写入，写入走工作台校验，不直接改 SQL 绕过阶段门槛。接口字段和状态规则见同一参考。

## 职责边界与交接

本 skill 寻找可能卖得好的商品和卖家。交付候选ID、商品/卖家URL、推荐依据、观察时间、证据路径及未知项。为判断潜力可以采样详情，但指定卖家的全量商品采集、SKU完整建档和上架资料整理交给 `xianyu-archive`。不默认将候选加入待上架队列。
用户直接给定卖家或商品并要求采集归档时，使用 `xianyu-archive`，无需重跑选品发现。现有工作台阶段只用于研究判断，不代表商品已准备好上架。

### 标准运行与交接

本 skill 的“完成”不是聊天中的方向判断，而是生成可被 `xianyu-archive` 直接消费的机器可读交付。执行时按以下规则：

1. 用户只给父词、条件或“自由研究”时，agent 自主选择和覆盖研究方向；用户不需要手动逐步确认。
2. 只有真实采样到的平台商品或卖家，才能进入候选；不能用新闻、搜索摘要或想象出的商品替代候选 URL。
3. 每个需求候选至少关联一个具体 candidate；每个 candidate 必须有 `candidate_id`、`kind`、`platform_id`、未改写的 `url`、观察时间、推荐依据和实际证据路径。没有这些字段时，只能报告“追加研究”，不能宣称已完成选品。
4. 研究结束必须写入 `discovery-batches/<batch_id>/discovery.json`，并按 [统一交接契约](references/contracts/contract.md) 校验。聊天回复可以摘要，但不能替代该文件。
5. 若后续使用 `xianyu-archive`，直接读取本批 `discovery.json`，按 `candidate_id` 采集；不得再次要求用户复制已经在 discovery 输出中的链接。若用户指定某 candidate，只处理指定项；未指定时处理本批全部候选。
6. 没有可靠商品链接、访问被限制或只得到二手报道时，交付状态必须是“追加研究/阻塞缺口”，明确缺口和下一步，不得把方向性判断包装成候选清单。

最终给用户的摘要只需包含：推荐候选、排除/暂缓项、每项的 URL 与证据、未知项、下一步以及本批文件路径。

## 执行循环

1. **认领方向。** 记录父词、地点、优先级、用户条件与未知项。父词可以是品牌、渠道、场景、人群或品类；“优先虚拟产品”不意味着品牌词必须扩成资料模板。重点优先级与采样进度分开保存。
2. **宽搜发现后扩词。** 先看父词的实际商品和交易类型，再沿商品名/规格、交易方式、地点、人群或问题扩词。每个词记录父词、维度、依据及方向。把想象出的词标为假设。按本轮目标分配覆盖，优先填补缺口；不要用固定词数冒充研究完整性。
3. **可追溯采样。** 通过可用的官方浏览器工具读取实际可见页面，先核对搜索词、排序、页面加载和无结果提示。记录商品ID、URL、观察时间、关键词、排序、位置、可见价格/想要数及原始文本，保留原始采集证据再导入。新轮次用独立批次前缀，不能写进历史第一轮统计。无显示值为 null；卖家未识别不算独立卖家；想要不等于销量，占位价不等于服务费。出现验证、频率限制或账号异常立即停止该平台采样，不绕过。
   - **强制访问节流：** 对闲鱼（goofish.com）页面实行全局串行访问；任意两个闲鱼页面访问/导航/刷新之间至少间隔 10 秒。搜索页、商品详情页、卖家页、登录页、重定向和失败页面都算一次访问；失败或空页面也必须等待 10 秒后才能访问下一页。禁止并发打开多个闲鱼页面，禁止通过多个标签页、请求或工具绕过该间隔。未满足间隔时必须等待，不得为了提速跳过。
4. **逐条初筛并留去向。** 方向内每条观察标为机会证据、排除或待核验；机会证据须关联至少一个具体商品/服务机会，排除与待核验须有理由。重复商品保留不同观察，不能当作多个独立需求信号。不要把搜索命中自动视为相关，也不要把不同品牌/规格/服务合并比较。完成一批时检查未初筛数，不能遗留而不报告。
5. **先筛需求候选。** 机会是“我们可能卖什么”，竞品链接是关联证据。把同一机会的多个竞品聚合。选品阶段优先比较同交易类型的想要、可核验商品销量和有时间间隔的增量。高想要且销量未知可以进入需求候选，写明可信度与未知项；异常低价保留需求信号并标注引流、多规格或货源疑点。免费服务不因免费排除，可以是返利驱动。成本、履约等在决定试卖前再核算，不阻挡需求候选入池。区分实际事实、卖家声称、估算及未知。根据缺口补搜/复查或提出必要问题；用户未确认的会员、交通、授权、进货条件不可推定。
6. **按门槛推进。** 待评估→追加研究→需求候选→待测试→测试中→保留/淘汰；可暂缓并记录恢复条件。进入待测试之前六项都要有证据支持且人工核验为通过。利润扣除进货、平台费用、包装运输、人工与售后；数字缺失不能勾通过。试卖方案写清价格、周期/样本量、预算、指标及停止条件。选品任务默认终点是有依据的需求候选清单或清楚的暂缓/淘汰结论，不能擅自开展上架和试卖。测试中须确有实际试卖；保留或测试后淘汰须记录真实周期、曝光、咨询、订单、退款、人工分钟与结论。未知数据不填0。
7. **收尾核对。** 运行状态检查，报告本轮观察数/独立商品数、初筛覆盖、机会阶段变化、排除/待核验数量和每个重点机会的下一步。如果只能停在追加研究，说明具体缺口；不得为了候选数量强行晋级。确保工作台中的判断与交付报告一致。

## 研究尺度

搜索头部结果有排序、地域、个性化及存续时间偏差。高累计想要仅是追加研究线索；可追加近期样本、同款竞争与间隔复采，不能从单次横截面断言出单率。用户要求重点研究时先处理该方向的待初筛和关键缺口，再扩充低优先级方向。没有明确商业意义的综合评分不替代逐项证据判断。

### 商品需求比较与推荐

1. 先扩展关键词，寻找同品牌、型号、规格和交易方式的多个独立卖家样本，排除自己账号和已处理商品。不同数量、规格、定价、地区与发布时间不同时明确标注，不直接比较累计指标。样本不足就继续搜索或标为追加研究，不为凑数量降低标准。
2. 每条记录可见的单品已售、想要数、浏览量和发布时间或上架时长；缺失为未知。单品已售与卖家账号累计卖出严格分开。上架时间相近、商品及价格可比时，优先考虑已售出更高或想要人数更多的商品；已售出不可见时用想要数作为需求代理，而非实际销量或成交率。
3. 在浏览量和想要数可比较且分母非零时，可计算想要/浏览作为兴趣比例，标注样本大小及不确定性；不称为成交转化率，不用想要数估算销量。缺上架时长、曝光或样本可比性时，不声称增长快或销售好。
4. 区分研究样本、需求候选和可交接上架的推荐：弱需求或未显示想要数仅列待观察，不因存在商品链接就晋级。需求信号不足时不把它放入自动交给归档的推荐清单；允许不足目标数量。候选需说明对比样本、指标、可比性与未知项，并以具体商品 URL 和证据支撑。
5. 确认高需求后评估可采购、成本、运费、平台费用、利润和履约；未知如实保留，未经核实不得宣称适合试卖或可上架。输出每一推荐的证据和可比较样本，附排除、暂缓原因；不混入食品。

## 详情与销量口径

详情采样仅取主商品区域，推荐区不计入主商品指标。记录详情原文、时间、精确/缩略想要、浏览、商品销量、账号累计卖出和发布时间。商品销量未显示则null；店铺已售出条目数、账号累计卖出及热销标签不当作商品销量。同店多个链接只算一个已识别卖家。搜索未显示、详情显示的变化属于覆盖补齐，不算增长；1万等缩略不与精确数计算增量，既有精确数保留原采集时间。

## 阶段交接数据契约（v1，优先于旧字段示例）

执行前读取 [统一交接契约](references/contracts/contract.md)，使用其中的JSON Schema校验输入与输出；金额用整数分，禁止与旧price字段混用。完整度和队列状态独立。
本阶段输出 discovery-batches/<batch_id>/discovery.json；候选商品和卖家按统一candidate结构交给采集建档，不以聊天摘要代替机器可读交付。
